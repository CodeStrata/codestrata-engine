8. Future-history leakage risk
This is real if R2 reuses the current journey observer or assesses the live worktree five times.

Path A — build_history_index() (safer if head is the snapshot)
engine/src/codestrata/application/incremental/history_index.py:

head = request.head or state.head_sha
Reads read_reachable_commit_metadata(root, head=head) → git log --no-merges <head>
(git_revision.py lines 175–190). Git reachability stops at that commit. Later first-parent children are not listed.
Time filter: window_start <= committer_unix <= evaluation_unix (select_included_commits).
Commits with committer_unix > evaluation_unix go to excluded_future_shas.
If each snapshot assess uses HistoryIndexRequest.head = S_i and evaluation_time is pinned (same clock is OK; graph bound is the SHA): S1 cannot see S2+ via git log.

Leakage still possible:

observe_local_git_state(root) always describes the current checkout, not request.head. If the index stores local_state.head_sha from the user worktree while request.head is S1, identity/freshness metadata can claim HEAD. Must pin observation to the snapshot root or to request.head.
Clock-skewed committer dates: a commit reachable from S1 with a timestamp after evaluation_time is dropped (future_timestamp); a commit not ancestor of S1 cannot appear if head=S1.
Path B — observe_repository() / _read_git() (unsafe for historical snapshots)
engine/src/codestrata/reporting/journey_observations.py _read_git():

git rev-parse HEAD
git log --numstat --pretty=format:COMMIT... -- .
window = "all_observed_local_commits"
evaluation_time_unix = JOURNEY_EVALUATION_TIME  # 2026-09-27 hardcoded
No head= argument. If the user repo is at HEAD, every call sees HEAD’s full history, including commits after S1–S4.

canonical_report_from_analysis() and _write_canonical_sidecars() call this when canonical_hotspots is missing. Five assesses of the same dirty repo + sidecar observe = five copies of HEAD history. That is future leakage for S1–S4.

Path C — assess file contents
LocalRepositoryScanner reads whatever files are on disk. Five assesses of the user worktree all see HEAD (and dirt). S1 source files would include S5 code. This is source-state leakage, not only history leakage.

What must be verified / changed
Materialize each snapshot as its own tree; assess that path.
For history, call build_history_index(HistoryIndexRequest(repository_root=snapshot_or_user_git_dir, head=S_i, evaluation_time=pinned)). Prefer GIT_DIR of the original repo + head=S_i so objects exist without copying .git.
Do not call observe_repository() on the user HEAD for historical slots.
Remove/replace JOURNEY_EVALUATION_TIME for production R2 (fixture-only).
Fixture: repo with 5 first-parent commits; S1 hotspot/churn must not include files only added at HEAD.
read_reachable_commit_metadata is not first-parent; that is OK for M24 window inside a snapshot. The snapshot list must still be first-parent rev-list.

13. Top implementation risks
Future-history leakage via observe_repository() / _read_git() (journey_observations.py) if historical slots observe user HEAD.
Source-state leakage if five assesses use LocalRepositoryScanner on the dirty user path instead of extracted trees.
Mutating the user worktree (checkout/worktree are forbidden in read_only_git.py; using raw git checkout would violate Engine Git policy).
HTML recomputing health if v2 builder starts ranking hotspots or subtracting metrics instead of copying envelope/comparison.
Two coverage systems (assessment heads vs envelope capability coverage) producing contradictory trust text.
current/previous only holds two runs (lifecycle.py MAX_VERSIONS = 2); stuffing five snapshots there will delete evidence.
Hardcoded JOURNEY_EVALUATION_TIME = 2026-09-27 making recency/freshness wrong on real repos.
M30 testing family vs four public outcomes — easy to grow a fifth headline.
Cloud/AI/Modernization packs still in builtin_analyzers / activation — they will still emit heads unless R2-A explicitly demotes them.
Compare CLI remains two files only — if trend is bolted onto compare without an orchestrator, users get no five-commit bundle and no slot preservation.
14. Final recommendation
R2 is a combination, in this order:

Projection / wiring (majority of baseline) — R2-A + R2-B. The Engine already has four OutcomeFamily values, findings, PAs, inventory, quality/maintainability evidence, M22–M31 modules, and a projector that is not allowed to compute health. The primary HTML is the wrong document.
Orchestration (majority of trend) — R2-C + R2-D. Pairwise compare and Git range/history APIs exist. Five first-parent snapshots, immutable extract, pinned inputs, and a bundle do not.
New analysis capability — essentially none. Do not add a family, score, or LLM-canonical path. The only new Engine-adjacent capability is read-only snapshot extract + series runner.
Baseline readiness: PARTIAL — one assess can produce most raw evidence; it cannot yet emit the R2 Engineering Health report as the customer primary artifact with M22/M25/M26/trust attached at assess time.

Five-commit trend readiness: NOT_READY — comparison and history libraries exist; snapshot isolation, first-parent selection, leakage-safe history-as-of-commit, and a five-slot bundle do not.
